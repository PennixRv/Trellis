# 跨平台思考指南（Cross-Platform Thinking Guide）

> **目的（Purpose）**：在平台特定假设变成错误前发现它们。

---

## 为什么重要（Why This Matters）

**大多数跨平台错误来自隐含假设：**

- 假定 shebang 可用 → 在 Windows 上失败
- 假定使用 `/` 路径分隔符 → 在 Windows 上失败
- 假定使用 `\n` 换行 → 行为不一致
- 假定命令可用 → `grep` 与 `findstr` 不同

---

## 平台差异清单（Platform Differences Checklist）

### 1. 脚本执行（Script Execution）

| 假设（Assumption） | macOS/Linux | Windows |
|------------|-------------|---------|
| Shebang (`#!/usr/bin/env python3`) | ✅ 可用 | ❌ 被忽略 |
| 直接执行（`./script.py`） | ✅ 可用 | ❌ 失败 |
| `python3` 命令 | ✅ 始终可用 | ⚠️ 可能需要 `python` |
| `python` 命令 | ⚠️ 可能是 Python 2 | ✅ 通常是 Python 3 |

**规则一**：对于面向用户的文档、帮助文本和错误消息，应当：

- 明确说明平台规则（Windows 使用 `python`，其他平台使用 `python3`）；或
- 使用代码采用的同一平台感知辅助函数/占位符生成命令。

```python
# BAD - Assumes shebang works
print("Usage: ./script.py <args>")
print("Run: script.py <args>")

# GOOD - Platform-aware wording
print("Usage: python on Windows, python3 elsewhere")
print("Run: {{PYTHON_CMD}} ./.trellis/scripts/task.py <args>")
```

**规则二**：在 init 时生成配置文件，应使用占位符和平台检测：

```typescript
// In template file (settings.json):
{ "command": "{{PYTHON_CMD}} .claude/hooks/script.py" }

// In configurator:
function getPythonCommand(): string {
  return process.platform === "win32" ? "python" : "python3";
}

function replacePlaceholders(content: string): string {
  return content.replace(/\{\{PYTHON_CMD\}\}/g, getPythonCommand());
}
```

**规则三**：从 JavaScript 在运行时调用 Python 时，动态检测平台：

```javascript
import { platform } from "os"

const PYTHON_CMD = platform() === "win32" ? "python" : "python3"
execSync(`${PYTHON_CMD} "${scriptPath}"`, { ... })
```

**规则四**：如果需要确认 Python 确实已安装，而不只是选择命令，应探测之后将要生成或执行的同一平台别名：

```typescript
function getPythonCommand(platform = process.platform): string {
  return platform === "win32" ? "python" : "python3";
}

function warnIfPythonTooOld(): void {
  const cmd = getPythonCommand();
  try {
    execSync(`${cmd} --version`, { stdio: "pipe" });
  } catch {
    // Missing Python is a separate error path; don't silently swap aliases.
  }
}
```

**规则五**：不要假定 AI CLI 使用的 Python 版本与 Shell 的 `python3` 相同。用户终端可能将 `python3` 解析为 Homebrew 3.11，但 AI CLI 宿主（包括企业分发的 Claude Code/Cursor）可能以最小 PATH 启动 Hook 子进程，将 `python3` 解析为 `/usr/bin/python3`，也就是 macOS 系统 3.9。分发模板必须面向合理的最低版本，或为 PEP 604 语法使用 `from __future__ import annotations`。硬规则和审查方法见 `cli/backend/script-conventions.md` 的 **CRITICAL: PEP 604 Annotations Require `from __future__ import annotations`**。

**规则六**：从 Python 调用 Python 时，使用 `sys.executable`：

```python
import sys
import subprocess

# BAD - Hardcoded command
subprocess.run(["python3", "other_script.py"])

# GOOD - Use current interpreter
subprocess.run([sys.executable, "other_script.py"])
```

### 2. 路径处理（Path Handling）

| 假设（Assumption） | macOS/Linux | Windows |
|------------|-------------|---------|
| `/` 分隔符 | ✅ 可用 | ⚠️ 部分情况下可用 |
| `\` 分隔符 | ❌ 转义字符 | ✅ 原生 |
| `pathlib.Path` | ✅ 可用 | ✅ 可用 |

**规则（Python）**：所有路径操作使用 `pathlib.Path`。

```python
# BAD - String concatenation
path = base + "/" + filename

# GOOD - pathlib
from pathlib import Path
path = Path(base) / filename
```

#### 逻辑键与文件系统路径（Logical key vs filesystem path，TypeScript）

路径字符串有两种不同角色，**必须区别处理**。

| 角色（Role） | 操作系统原生形式（Windows 使用 `\`） | 始终使用 POSIX（`/`） |
|------|---------------------------|--------------------|
| 文件系统调用中的 `fs.readFileSync(p)` / `path.join(cwd, x)` | ✅ 必需 | ❌ 在 Windows 上可能失败 |
| `Map<relPath, content>` 键、JSON 字段、哈希字典键及其他跨操作系统持久化内容 | ❌ 跨操作系统不匹配 | ✅ 必需 |

**规则**：路径字符串跨操作系统或持久化时（被另一操作系统消费的 Map 键、JSON 字段、哈希字典键），规范化为 POSIX。直接传给 `fs.*` 时保留操作系统原生形式。

**唯一事实来源**：`packages/cli/src/utils/posix.ts` 导出 `toPosix(p)`。不要在每个 `path.join` 位置散落 `replaceAll('\\', '/')`，而是在边界处使用一次 `toPosix`：收集器出口（Map 键进入哈希字典时）或写入时（`JSON.stringify` 前的 `saveHashes`）。

```typescript
// BAD - logical key carries OS-native separator
function collectTemplates(): Map<string, string> {
  const files = new Map<string, string>();
  for (const entry of walk(dir)) {
    files.set(path.join(".opencode", entry), readFile(entry));  // \ on Windows
  }
  return files;
}

// GOOD - normalize at the boundary
import { toPosix } from "../utils/posix.js";

function collectTemplates(): Map<string, string> {
  const files = new Map<string, string>();
  for (const entry of walk(dir)) {
    files.set(toPosix(path.join(".opencode", entry)), readFile(entry));
  }
  return files;
}

// ALSO ACCEPTABLE - write-side defense (for storage helpers like saveHashes)
function saveHashes(cwd: string, hashes: Record<string, string>): void {
  const normalized = Object.fromEntries(
    Object.entries(hashes).map(([k, v]) => [toPosix(k), v])
  );
  fs.writeFileSync(getHashesPath(cwd), JSON.stringify(normalized, null, 2));
}
```

**常见问题**：`path.relative(cwd, fullPath)` 在 Windows 上会产生 `\`。如果随后将该字符串用作哈希字典查找键（`hashes[relPath]`），必须先使用 `toPosix`，否则 Windows 上会查找失败。

### 3. 换行符（Line Endings）

| 格式（Format） | macOS/Linux | Windows | Git |
|--------|-------------|---------|-----|
| `\n`（LF） | ✅ 原生 | ⚠️ 部分工具支持 | ✅ 规范化 |
| `\r\n`（CRLF） | ⚠️ 多余字符 | ✅ 原生 | 转换 |

**规则一**：使用 `.gitattributes` 强制统一换行符。

```gitattributes
* text=auto eol=lf
*.sh text eol=lf
*.py text eol=lf
```

**规则二**：跨平台计算哈希或比较**内容**时，计算哈希前先规范化换行符。`.gitattributes` 只控制 Git checkout；用户、脚本或 `core.autocrlf=true` 写入的文件仍可能是 CRLF，对其他内容相同的文件而言，`sha256(LF)` ≠ `sha256(CRLF)`。

```typescript
// BAD - Windows users with autocrlf=true get a different hash
export function computeHash(content: string): string {
  return createHash("sha256").update(content, "utf-8").digest("hex");
}

// GOOD - normalize before hashing so logical content hashes identically
export function computeHash(content: string): string {
  const normalized = content.replace(/\r\n/g, "\n");
  return createHash("sha256").update(normalized, "utf-8").digest("hex");
}
```

哈希跨操作系统边界时均应用此规则，包括模板哈希字典、JSON 中的内容指纹以及远端注册表完整性检查。

### 4. 环境变量（Environment Variables）

| 变量（Variable） | macOS/Linux | Windows |
|----------|-------------|---------|
| `HOME` | ✅ 已设置 | ❌ 使用 `USERPROFILE` |
| `PATH` 分隔符 | `:` | `;` |
| 大小写敏感性 | ✅ 区分大小写 | ❌ 不区分大小写 |

**规则一**：使用 `pathlib.Path.home()`，不要直接依赖环境变量。

```python
# BAD
home = os.environ.get("HOME")

# GOOD
home = Path.home()
```

**规则二**：向 Shell 命令注入环境变量时，针对实际解析命令的 Shell 生成前缀。不要只依据操作系统选择语法。Windows 上的 AI 工具“Bash”界面可能通过 PowerShell、Git Bash、MSYS2 或其他类 POSIX Shell 执行。

```javascript
// BAD - breaks when the host shell is PowerShell
command = `export TRELLIS_CONTEXT_ID=${shellQuote(contextKey)}; ${command}`;

// GOOD - shell-dialect-aware command prefix
const prefix = process.platform === "win32" && !isWindowsPosixShell(process.env)
  ? `$env:TRELLIS_CONTEXT_ID = ${powershellQuote(contextKey)}; `
  : `export TRELLIS_CONTEXT_ID=${shellQuote(contextKey)}; `;
command = `${prefix}${command}`;
```

在 Windows 上，将 `MSYSTEM`、`MINGW_PREFIX`、`OSTYPE=msys|mingw|cygwin`、`SHELL=...bash` 或平台特定的 Git Bash 设置视为 POSIX Shell 信号。没有 POSIX Shell 信号时，将 PowerShell 作为 Windows 默认值。

重复注入检测也必须感知 Shell。只匹配 `export VAR=` 的保护逻辑会遗漏 PowerShell 的 `$env:VAR = ...` 形式，并可能将已经正确的命令再次包装。

### 5. 命令可用性（Command Availability）

| 命令（Command） | macOS/Linux | Windows |
|---------|-------------|---------|
| `grep` | ✅ 内置 | ❌ 不可用 |
| `find` | ✅ 内置 | ⚠️ 语法不同 |
| `cat` | ✅ 内置 | ❌ 使用 `type` |
| `tail -f` | ✅ 内置 | ❌ 不可用 |

**规则**：可行时使用 Python 标准库替代 Shell 命令。

```python
# BAD - tail -f is not available on Windows
subprocess.run(["tail", "-f", log_file])

# GOOD - Cross-platform implementation
def tail_follow(file_path: Path) -> None:
    """Follow a file like 'tail -f', cross-platform compatible."""
    with open(file_path, "r", encoding="utf-8", errors="replace") as f:
        f.seek(0, 2)  # Go to end
        while True:
            line = f.readline()
            if line:
                print(line, end="", flush=True)
            else:
                time.sleep(0.1)
```

### Agent 沙箱中的可选提示检查（Optional Advisory Checks in Agent Sandboxes）

即使用户的普通终端可以访问网络，AI CLI 子进程也可能禁用出站网络。如果本地 CLI 已提供所需信息，优先使用本地 CLI 探测，而不是可选的网络探测。

**规则一**：失败的可选提示检查不得消耗每会话一次的标记。只有脚本解析出可用值并能够作出预期决策后才写入标记，否则沙箱/网络的临时错误会隐藏本会话剩余时间的提示。

**规则二**：如果本地命令可以提供所需值，使用短超时和捕获输出进行尝试。例如，`trellis --version` 已经执行 CLI 版本比较逻辑，可以支持可执行的更新提示，而不必重复 npm registry 解析。

**规则三**：提示检查失败时保持静默。面向用户的上下文输出不能因提示检查未完成而失败或变得嘈杂。

### 6. 文件编码（File Encoding）

| 默认编码（Default Encoding） | macOS/Linux | Windows |
|------------------|-------------|---------|
| 终端 | UTF-8 | 常为 CP1252 或 GBK |
| 文件 I/O | UTF-8 | 系统区域设置 |
| Git 输出 | UTF-8 | 可能不同 |

**规则**：始终显式指定 `encoding="utf-8"`，并使用 `errors="replace"`。

> **清单**：编写会输出非 ASCII 内容的脚本时，是否配置了 stdout 编码？
> 具体模式见 `backend/script-conventions.md`。

```python
# BAD - Relies on system default
with open(file, "r") as f:
    content = f.read()

result = subprocess.run(cmd, capture_output=True, text=True)

# GOOD - Explicit encoding with error handling
with open(file, "r", encoding="utf-8", errors="replace") as f:
    content = f.read()

result = subprocess.run(
    cmd,
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="replace"
)
```

**Git 命令（Git commands）**：强制使用 UTF-8 输出编码：

```python
# Force git to output UTF-8
git_args = ["git", "-c", "i18n.logOutputEncoding=UTF-8"] + args
result = subprocess.run(
    git_args,
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="replace"
)
```

## 提交前清单（Pre-Commit Checklist）

提交跨平台代码前：

- [ ] 面向用户的 Python 调用感知平台（Windows 使用 `python`，其他平台使用 `python3`），或使用 `{{PYTHON_CMD}}`
- [ ] Python 调用 Python 子进程时使用 `sys.executable`
- [ ] 所有路径使用 `pathlib.Path`
- [ ] 没有硬编码路径分隔符（`/` 或 `\`）
- [ ] 用作逻辑/持久化键的路径字符串（Map 键、JSON 字段、哈希字典键）经 `toPosix()` 规范化；`fs.*` 调用保留操作系统原生路径
- [ ] 跨操作系统内容哈希在计算前规范化换行符（`\r\n` → `\n`）
- [ ] 可能受旧格式污染的跨操作系统 JSON 带有 `__version` 标记，加载器丢弃未知或旧版本
- [ ] 平台特定命令都有替代路径（如 `tail -f`）
- [ ] 可选提示检查失败时不消耗每会话一次的标记
- [ ] 所有文件 I/O 显式指定 `encoding="utf-8"` 和 `errors="replace"`
- [ ] 所有子进程调用显式指定 `encoding="utf-8"` 和 `errors="replace"`
- [ ] Git 命令使用 `-c i18n.logOutputEncoding=UTF-8`
- [ ] 外部工具 API 格式已经文档核验
- [ ] 文档与代码行为一致
- [ ] 已搜索所有受影响位置

### 7. 外部工具 API 合同（External Tool API Contracts）

集成外部工具（Claude Code、Cursor 等）时，它们的 API 合同属于**隐含假设**。

**规则**：从官方文档核验 API 格式，不要猜测。

```python
# BAD - Guessed format
output = {"continue": True, "message": "..."}

# GOOD - Verified format from documentation
output = {
    "hookSpecificOutput": {
        "hookEventName": "SessionStart",
        "additionalContext": "..."
    }
}
```

> **警告**：不同 Hook 类型可能有不同的输出格式。
> 始终检查每个 Hook 事件的具体文档。

## 跨平台持久化 JSON：Schema 迁移标记（Cross-Platform Persisted JSON: Schema Migration Sentinel）

当 JSON 文件可能跨操作系统读写（提交到 Git、通过云同步或在机器之间复制），并且用户磁盘上可能已有带跨平台污染的旧格式（Windows 风格键、由 CRLF 产生的哈希、本地编码字符串）时，增加 `__version` 标记，让加载器丢弃旧格式，由写入器重新生成干净数据。

**为什么不原地迁移？**路径键迁移（`\\` → `/`）、哈希输入迁移（CRLF → LF 后重新计算）和编码修复相互关联，直接翻译旧载荷可能产生错误值。丢弃并重新生成是**安全的**：数据可以从磁盘重新计算，`loadX` 返回 `{}` 会触发已有 init/update 路径重建规范条目。

```typescript
const SCHEMA_VERSION = 2;
type StoredV2 = { __version: number; hashes: Record<string, string> };

export function loadHashes(cwd: string): Record<string, string> {
  const file = getHashesPath(cwd);
  if (!fs.existsSync(file)) return {};

  try {
    const parsed = JSON.parse(fs.readFileSync(file, "utf-8")) as unknown;

    // Reject legacy flat format (no __version) and unknown versions.
    // The next saveHashes / initializeHashes will write a fresh v2 file.
    if (
      !parsed ||
      typeof parsed !== "object" ||
      (parsed as StoredV2).__version !== SCHEMA_VERSION ||
      typeof (parsed as StoredV2).hashes !== "object"
    ) {
      return {};
    }
    return (parsed as StoredV2).hashes;
  } catch {
    return {};
  }
}

export function saveHashes(cwd: string, hashes: Record<string, string>): void {
  const payload: StoredV2 = { __version: SCHEMA_VERSION, hashes };
  fs.writeFileSync(getHashesPath(cwd), JSON.stringify(payload, null, 2));
}
```

**适用场景**：
- 哈希字典/内容指纹（例如 `.template-hashes.json`）
- 可从权威来源重新计算过期条目的缓存文件
- 格式变化与跨平台修复相关的其他跨操作系统持久化文件

**不适用场景**——丢失数据会伤害用户时（任务状态、草稿、用户输入的设置）。这些数据应使用真实迁移。只有数据可重新计算时，标记加丢弃才安全。

**参考（Reference）**：`packages/cli/src/utils/template-hash.ts` 的 v2 封装结构。

## JSON/外部数据防御性检查（JSON/External Data Defensive Checks）

解析 JSON 或外部数据时，TypeScript 类型**只在编译期生效**，运行时数据可能不匹配。

**规则**：使用必需字段前始终进行防御性检查。

```typescript
// BAD - Trusts TypeScript type definition
interface MigrationItem {
  from: string;  // TypeScript says required
  to?: string;
}

function process(item: MigrationItem) {
  const path = item.from;  // Runtime: could be undefined!
}

// GOOD - Defensive check before use
function process(item: MigrationItem) {
  if (!item.from) return;  // Skip invalid data
  const path = item.from;  // Now guaranteed
}
```

**适用场景**：
- 解析 JSON 文件（manifest、配置）
- API 响应
- 用户输入
- 任何外部来源的数据

**模式**：先检查是否存在 → 再使用

```typescript
// Filter pattern - skip invalid items
const validItems = items.filter(item => item.from && item.to);

// Early return pattern - bail on invalid
if (!data.requiredField) {
  console.warn("Missing required field");
  return defaultValue;
}
```

## 常见错误（Common Mistakes）

### 1. “在我的 Mac 上可以工作”（“It works on my Mac”）

```python
# Developer's Mac
subprocess.run(["./script.py"])  # Works!

# User's Windows
subprocess.run(["./script.py"])  # FileNotFoundError
```

### 2. “shebang 应该能处理”（“The shebang should handle it”）

```python
#!/usr/bin/env python3
# This line is IGNORED on Windows
```

### 3. “我已经更新模板了”（“I updated the template”）

```
src/templates/script.py  ← Updated
.trellis/scripts/script.py  ← Forgot to sync!
```

### 4. “Python 3 总是 python3”（“Python 3 is always python3”）

```bash
# Developer's Mac/Linux
python3 script.py  # Works!

# User's Windows (Python from python.org)
python3 script.py  # 'python3' is not recognized
python script.py   # Works!

# Trellis docs/config should say the rule, not guess one alias everywhere
{{PYTHON_CMD}} script.py
```

### 5. “任何地方默认都是 UTF-8”（“UTF-8 is the default everywhere”）

```python
# Developer's Mac (UTF-8 default)
subprocess.run(cmd, capture_output=True, text=True)  # Works!

# User's Windows (GBK/CP1252 default)
subprocess.run(cmd, capture_output=True, text=True)  # Garbled Chinese/Unicode
```

> **注意**：stdout 编码也会受到影响。修复方法见 `backend/script-conventions.md`。

## 恢复：发现平台错误时（Recovery: When You Find a Platform Bug）

2. **搜索相似模式**（grep 代码库）
3. **用新模式更新本指南**

## 发布清单：版本化文件（Release Checklist: Versioned Files）

发布新版本时，确保创建或更新**所有版本化文件**：

- [ ] `src/migrations/manifests/{version}.json`——迁移清单存在
- [ ] 清单包含正确的版本、描述和变更日志
- [ ] `pnpm build` 将迁移清单复制到 `dist/`
- [ ] 测试从较旧版本升级的路径（不只相邻版本）

**原因（Why this matters）**：迁移清单缺失会让从较旧版本升级的用户遇到 "path undefined" 错误。

```bash
# Verify all expected manifests exist
ls src/migrations/manifests/

# Test upgrade path
node -e "
const { getMigrationsForVersion } = require('./dist/migrations/index.js');
console.log('From 0.2.12:', getMigrationsForVersion('0.2.12', 'CURRENT').length);
"
```

## 发布清单：内置资产（Release Checklist: Bundled Assets）

发布说明或文档宣称某项资产内置、自动安装或随 Trellis 提供时，核验整个分发路径：

- [ ] 源文件存在于将打标签的分支，而非仅在其他分支、文档子模块或 marketplace 目录树中
- [ ] `pnpm build` 将资产复制到 `dist/templates/**`
- [ ] `npm pack --dry-run --json` 包含预期的 `dist/**` 路径
- [ ] 构建后的可执行文件能在新建临时仓库中安装资产
- [ ] `.trellis/.template-hashes.json` 跟踪生成资产的路径
- [ ] 临时仓库中 `trellis update --dry-run` 报告 `Already up to date!`

**原因（Why this matters）**：文档和变更日志可以独立于分发模板所属代码分支更新。文档可能已经宣称功能内置，而发布的 npm 包仍缺少相应文件。

```bash
pnpm --filter @pennixrv/trellis build

cd packages/cli
npm pack --dry-run --json | grep 'dist/templates/common/bundled-skills/<skill>/SKILL.md'
cd ../..

tmpdir=$(mktemp -d /tmp/trellis-built-bin-smoke-XXXXXX)
printf '{"name":"trellis-smoke","version":"0.0.0"}\n' > "$tmpdir/package.json"
git -C "$tmpdir" init -q
(
  cd "$tmpdir"
  node /path/to/Trellis/packages/cli/bin/trellis.js init -u smoke --yes --claude --codex
  test -f .claude/skills/<skill>/SKILL.md
  test -f .agents/skills/<skill>/SKILL.md
  grep -q '<skill>' .trellis/.template-hashes.json
  node /path/to/Trellis/packages/cli/bin/trellis.js update --dry-run
)
```
